# 33 · Distributed unique IDs: Snowflake, ULID, UUIDv7, Segment — which, when, why — comprehension

> Companion notes: [`notes.md`](notes.md). Grounded in the **real** `shopflow-id` module: `SnowflakeIdGenerator.java` (41ms+10node+12seq, clock-backwards refusal), `UlidGenerator.java` (48ms+80rand base32, monotonic-in-ms), `Uuidv7Generator.java` (RFC 9562), `SegmentIdGenerator.java`+`SegmentAllocator.java` (Hi/Lo block allocation). ShopFlow's `orders` table itself uses **DB identity** (`bigint generated by default as identity`) + a UUID `order_ref` — this module is the toolkit for when you need coordination-free, time-sortable ids.
> **Theme:** har node ko unique id chahiye bina aapas mein baat kiye — aur id ka **shape** DB index performance decide karta.

---

## Scenario (read cold)

> *A review of the `shopflow-id` module: "we need unique ids across many nodes with no central coordinator — compare the four generators and say which you'd use for what." Read once, then answer.*

Every service needs unique ids, and at scale you can't ask a central sequence for each one (that's a bottleneck and a single point of failure). You also learn, painfully, that **the id's shape affects the database**: a **random** id (UUIDv4) used as a primary key **scatters inserts all over the index B-tree** — page splits, poor cache locality, write amplification. A **time-ordered** id keeps new rows at the **tail** of the index, where inserts are cheap. So the module offers four generators, each a different point on "coordination vs sortability vs size."

**(1) Snowflake — 64-bit, time-ordered, node-partitioned.** Layout: `[1 unused][41-bit ms since a custom epoch][10-bit node id][12-bit per-ms sequence]`. The timestamp on top makes ids **sortable by creation time** (ideal PK — inserts hit the end of the B-tree); the **node id** (0..1023) lets up to 1024 generators run **without coordinating**; the **12-bit sequence** allows **4096 ids per node per millisecond**. The custom epoch makes the 41 bits last ~**69 years**. Two hazards it must handle, both in the code: **sequence exhausted within a millisecond** → spin to the next ms (never reuse a number); and the **clock moving backwards** (an NTP step) → it **refuses** (throws) rather than risk a duplicate / a time-travelling id.

**(2) ULID — 128-bit, lexicographically sortable string, no node id.** `[48-bit ms → 10 chars][80 bits random → 16 chars]`, as a 26-char **Crockford base32** string (alphabet chosen so symbol order == character order == lexicographic order). Over UUIDv4: the **time prefix makes string order == time order**, so inserts stay at the tail; and unlike Snowflake it needs **no node-id coordination** (the 80 random bits make collisions astronomically unlikely). It's **monotonic within a millisecond**: rather than fresh randomness (which could sort two same-ms ids out of order), it **increments the previous random suffix by one**, so later always sorts after earlier. Cost: 26 chars vs a 64-bit long.

**(3) UUIDv7 — a standard UUID that's time-ordered.** RFC 9562: a normal `UUID` whose high bits are a **48-bit ms timestamp**, so it's time-sortable like ULID **but drops straight into anything that already expects a `UUID`** (columns, libraries, APIs). Use it over UUIDv4 for the same index-locality reason; over Snowflake when you want a **standard UUID** and 128 bits is fine.

**(4) Segment (Hi/Lo) — a DB counter handed out in blocks.** A `SegmentAllocator` does **one atomic DB statement** — `UPDATE id_segment SET next = next + :size WHERE name=:name RETURNING next` — to reserve a whole **block** of ids; the generator then hands ids out **locally** from that block until it runs dry, then grabs the next block. So the DB round-trip is **once per blockSize**, not per id → near-zero per-id cost, **dense** ids. Trade-offs the code names: ids are **not globally time-sortable** (they're per-generator sequential), and a **restart wastes the rest of the current block** (gaps) — which is fine, because ids only need to be **unique, not gap-free**. Bigger blocks = fewer DB hits but more waste on restart.

The through-line: there is no universally best id. You trade **coordination** (Snowflake needs unique node ids; Segment needs the DB; ULID/UUIDv7 need neither), **sortability** (all but Segment are time-ordered), **size** (64-bit vs 128-bit vs 26-char), and **density**. Pick by what the id must do — and remember a random PK is a database performance bug, not just a cosmetic choice.

## Questions

### A — Literal
1. Why is a random UUIDv4 a poor choice as a database primary key, and what property fixes it?
2. Spell out Snowflake's 64-bit layout and what each field buys (coordination, sortability, throughput).
3. How does the Segment allocator make the per-id DB cost near zero, and what does it give up?

### B — Inference
4. Snowflake **refuses** when the clock moves backwards instead of just using the old timestamp. Why is refusing the safer choice, and what does it protect?
5. ULID increments the previous random suffix (rather than drawing fresh randomness) for ids in the same millisecond. What exact problem does that solve, and why does it matter for a DB key?

### C — Trade-off
6. Snowflake (64-bit, needs a node id) vs ULID (128-bit, no node id). What does each cost and buy, and when would you pick each?
7. Segment ids are dense and cheap but **not** time-sortable, and waste a block on restart. For what kind of table is that a great fit, and for what kind is it a bad one?

### D — Transfer / extension
8. You're choosing an id scheme for ShopFlow's `orders` table (today: DB identity + a UUID `order_ref`). You want time-sortable PKs, no central bottleneck, and compatibility with code that expects a UUID. Which generator, and what do you give up vs Snowflake?
9. Snowflake's node id is 10 bits (0..1023). You deploy on Kubernetes where pods come and go. What's the operational hazard, and give two ways to assign node ids safely so two live generators never share one.

### E — Spot-the-flaw
10. A dev switches the primary key of a high-write table from a time-ordered id to **UUIDv4** "for simplicity, they're unique too." Inserts are fine in staging; in prod, write latency climbs and the DB's cache hit-rate drops over weeks. Explain the mechanism, and why it only shows up at scale/over time.

## Model answers

<details>
<summary>A — Literal</summary>

1. UUIDv4 is **random**, so successive inserts land at **random positions** across the index B-tree → **page splits**, poor cache locality, and write amplification (the hot part of the index is scattered, not cached). The fix: a **time-ordered** id, so new rows sort to the **end** of the index where inserts are sequential and cache-friendly.
2. `[1 unused][41-bit ms since custom epoch][10-bit node id][12-bit sequence]`. The **41-bit timestamp** on top → **time-sortable** (cheap tail inserts) and ~69 years of range; the **10-bit node id** → up to **1024 generators with no coordination**; the **12-bit sequence** → **4096 ids per node per ms** of throughput before it must spin to the next ms.
3. It reserves a **block** of `blockSize` ids with **one atomic `UPDATE ... RETURNING`**, then hands ids out **locally** from that block — so the DB is hit **once per block**, not per id (per-id cost ≈ 0). It gives up **global time-sortability** (ids are per-generator sequential, interleaved arbitrarily across generators) and **gap-freeness** (a restart abandons the rest of the current block).
</details>

<details>
<summary>B — Inference</summary>

4. If the clock jumps **backwards** (NTP correction) and you kept generating, you could **re-issue timestamps you've already used** → with the same node+sequence, a **duplicate id**, or at least an id that sorts *before* earlier ones (breaking the time-order invariant). Refusing (throwing) **protects uniqueness and monotonicity** — it's better to fail loudly for a few ms than to silently mint a duplicate primary key. (A production variant may **wait** a few ms if the drift is tiny, but never reuse.)
5. Within a single millisecond the timestamp bits are identical, so ordering depends on the random bits. **Fresh** randomness for two same-ms ids could sort them **out of creation order** (the second could be numerically smaller). Incrementing the previous suffix guarantees the **later id is always greater**, so **lexicographic/numeric order == creation order even within a ms**. For a DB key that matters because it keeps **inserts strictly at the tail** (no occasional mid-index insert) and makes "order by id" a true time order.
</details>

<details>
<summary>C — Trade-off</summary>

6. **Snowflake:** compact **64-bit** (fits a `bigint`, smaller index, less storage/bandwidth), very high throughput, time-sortable — **but** needs a **unique node id** per generator (coordination/ops burden, and only 1024 of them). **ULID:** **no coordination** (just randomness), time-sortable, URL-safe string — **but 128 bits / 26 chars** (bigger keys, more storage, slightly slower compares). **Pick Snowflake** when you control node assignment and want the smallest fast integer key at high volume; **pick ULID** when you want zero coordination and don't mind 128-bit string keys (microservices where assigning node ids is a pain).
7. **Great fit:** an internal, high-write table where ids only need to be **unique and cheap** and you never rely on id order for time (e.g. a log/detail table, or any PK where you sort by an explicit `created_at`). **Bad fit:** a table where you **want the PK to encode time** (range scans "recent first" by id, keyset pagination by id) or where **gaps are confusing/meaningful** (externally-visible sequential invoice numbers that auditors expect to be contiguous) — Segment's gaps and non-time-order break both.
</details>

<details>
<summary>D — Transfer / extension</summary>

8. **UUIDv7** — it's **time-sortable** (tail inserts, good index locality), needs **no node-id coordination** or central allocator (no bottleneck), and is a **standard `UUID`**, so it slots into the existing `order_ref`/UUID-shaped code and tooling with no type changes. **Vs Snowflake you give up:** the compact 64-bit key (UUIDv7 is 128-bit → bigger index/storage) and Snowflake's higher same-ms throughput ceiling; you gain not having to assign/track node ids. (For an orders table, the no-coordination + UUID-compatibility usually wins.)
9. **Hazard:** if two pods ever get the **same node id** (0..1023), their ids can **collide** (same timestamp+node+sequence). With pods churning, naive assignment (e.g. hash of hostname, or a config value copied across pods) risks reuse. **Two safe ways:** **(a)** lease node ids from a **coordination service** (ZooKeeper/etcd/DB) — each starting pod atomically claims a free id and renews a lease, releasing it on shutdown/expiry; **(b)** derive the node id from a **guaranteed-unique, stable ordinal** — e.g. a StatefulSet's pod ordinal, or the low bits of the pod IP if the ranges guarantee uniqueness — so two live generators can't map to the same 10-bit value. Either way the invariant is **"no two *simultaneously live* generators share a node id."**
</details>

<details>
<summary>E — Spot-the-flaw</summary>

10. UUIDv4 keys are **random**, so each insert targets a **random leaf** of the primary-key B-tree. Early on (small index, fits in cache) it's fine — staging and week one look normal. As the table grows past RAM, those random inserts hit **cold pages** scattered across the index → constant **page splits**, **cache misses**, and extra I/O per insert; the working set is the **whole index** instead of just the tail, so the buffer-cache **hit-rate falls** and **write latency climbs**. It shows up **at scale/over time** because the pathology only bites once the index is **too big to cache** and inserts can no longer stay hot — exactly the "fast in staging, degrades in prod over weeks" signature (cf. topic 31's index cliff). A **time-ordered** id (Snowflake/ULID/UUIDv7) keeps inserts at the **tail** (a small, hot, cacheable region), avoiding it. "They're unique too" ignored that **uniqueness isn't the job of a key's *shape* — locality is.**
</details>

## Interview concepts is passage se
- **Coordination-free unique ids** — central sequence = bottleneck/SPOF.
- **Id shape ↔ DB index** — random PK scatters inserts (page splits, cache misses); time-ordered = tail inserts.
- **Snowflake** — 41ms+10node+12seq; 4096/ms/node, 1024 nodes, ~69y; clock-backwards refusal; node-id coordination.
- **ULID / UUIDv7** — time-sortable, no node id; ULID 26-char base32 + same-ms monotonic; UUIDv7 = standard UUID.
- **Segment / Hi-Lo** — block allocation (`UPDATE ... RETURNING`), 1 DB hit per block, dense, not time-sortable, gaps OK.
- **Node-id assignment** — lease (etcd/ZK) or stable ordinal; never two live generators on one id.
- **Decision axes** — coordination vs sortability vs size vs density.

**Interviewer's lens:** kya tu id ke **shape ka DB index pe asar** jaanta (random UUID = write bottleneck), Snowflake ka bit-layout + clock/sequence hazards bol sakta, aur coordination/sortability/size ke trade-off se **sahi generator** chun sakta.

> Interview line: *"Scale pe central sequence bottleneck hai, to coordination-free id chahiye — aur id ka **shape DB ko affect karta**: random UUIDv4 PK inserts ko B-tree bhar scatter karta (page splits, cache miss), time-ordered id tail pe rakhta. `shopflow-id` mein 4 hain: **Snowflake** (64-bit = 41ms+10node+12seq, 4096/ms/node, clock-backwards pe refuse, node-id coordination chahiye), **ULID** (128-bit base32, time-sortable, no node-id, same-ms mein suffix increment karke monotonic), **UUIDv7** (standard UUID jo time-ordered — UUID-expecting code mein drop-in), aur **Segment/Hi-Lo** (DB se block allocate `UPDATE..RETURNING`, 1 hit per block, dense par not time-sortable, restart pe gap). Orders ke liye main UUIDv7 lunga — time-sortable + no coordination + UUID-compatible, Snowflake ke 64-bit compactness ko chhod ke."*
